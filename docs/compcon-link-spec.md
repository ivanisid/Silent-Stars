# Зв'язок апки з акаунтом COMP/CON і вхід гравця в модуль Foundry

Перед початком: прочитати `CLAUDE.md`, `docs/overview.md`, `docs/foundry-sync.md`. Зразки:
імпорт файлу COMP/CON у слоти ангару (`client/src/pilot/compconFile.js`, `slotImport.js`,
`mechMerge.js`), синхронізація з Foundry (`supabase/functions/foundry-sync`,
`foundry-module/silent-stars-sync`).

Статус: **погоджено 17.10.2026** (рішення — §0.1). Написи §3–4 затверджено; нові написи, яких
там немає, затверджує користувач до коду (CLAUDE.md: лише продуктові тексти, без пояснювальних
підписів).

Завдання (від користувача):
1. Гравець змінює білд у COMP/CON і не завантажує файл в апку щоразу вручну.
2. Три джерела правди: апка — мана, PR і стан пілота й меха; COMP/CON — білд; Foundry — бій.
3. Гравець підключає свій акаунт COMP/CON в апці; апка й гравець бачать, що синхронізується,
   а що ні. Ці дані використовує й модуль Foundry.
4. Гравець входить у модуль Foundry через акаунт апки (не через COMP/CON) і сам бачить стан
   синхронізації. Модуль — хаб на зразок вікна Lancer Comp/Con Sync: список персонажів ліворуч,
   їхня інформація праворуч.
5. Дії гравця мають бути зрозумілими — їхня послідовність прописана в §3.

## 0.1. Рішення користувача (17.10.2026)

1. **LL** — джерело правди апка. Рівень з COMP/CON не приймається; якщо він відрізняється від LL
   в апці, апка показує попередження.
2. **Нова версія** — лише кнопкою апки `СИНХРОНІЗУВАТИ З COMP/CON`; автоматичної перевірки
   немає. Прийняття — вручну.
3. **Ручне завантаження JSON** лишається запасним шляхом.
4. **Оновлення актора у Foundry** — гравець сам у хабі; ГМ теж може. ГМ у грі для цього не
   потрібен (§5).
5. **Бонд** — лише в апці, зокрема архетип, сили й burdens в акторі Foundry (§5.1).
6. Неофіційний API COMP/CON — на ризик проєкту.
7. **Акаунт COMP/CON** лише дає апці бачити пілотів у хмарі й обрати, яких із них прив'язати —
   як у модулі Lancer Comp/Con Sync. Прив'язка пілота — одним із двох способів (§3.2):
   вибір зі списку акаунта або **share code** без входу в акаунт (рішення користувача
   17.10.2026: синхронізація лише за кодом — «дуже добре і треба»).
8. **Підключення COMP/CON** — новий блок `COMP/CON LINK` в Account manager (§3.1).
9. **Статуси на екрані вибору пілотів** (`/pilots`) — §3.5.
10. **Прив'язка пілота, мехів до слотів, синхронізація й перегляд змін** — у профілі пілота
    (`/pilots/<id>`).
11. **Хаб у Foundry** (§4): вхід — нік і пароль апки; гравець бачить своїх пілотів, ГМ — усіх;
    хаб замінює вікно «Зв'язки з апкою»; права панель — дані з файлу COMP/CON (LL, HULL / AGI /
    SYS / ENG, таланти, ліцензії, скіли, корбонуси, бонд) плюс мана, PR і мехи по слотах з апки;
    дії — `СТВОРИТИ АКТОРА` і `СИНХРОНІЗУВАТИ ЗМІНИ З COMP/CON`.

Написи, які дав користувач (дослівно): `COMP/CON LINK`; «Прив'яжіть свій акаунт з COMP/CON для
синхронізації стану персонажів.»; «Рівень персонажу в файлі не відповідає рівню вашого
персонажу.»; `СИНХРОНІЗУВАТИ З COMP/CON`; `СИНХРОНІЗУВАТИ ЗМІНИ З COMP/CON`; `СТВОРИТИ АКТОРА`;
статуси §3.5. Решта написів — §9.

## 0. Встановлені факти (17.10.2026)

1. Файл у хмарі COMP/CON оновлюється **лише вручну** — спеціальною кнопкою синхронізації в
   COMP/CON (перевірено користувачем). Автозбереження в хмару немає.
2. Share code показує версію, яку гравець опублікував за кодом; модуль Lancer Comp/Con Sync
   бачить її лише після цього (перевірено користувачем).
3. Повторний імпорт актора в Foundry (і системний, і через Lancer Comp/Con Sync) наповнює ХП,
   структуру, стрес і ремкомплекти до максимуму, обнуляє heat, burn, overshield і створює
   предмети наново (код `Agraael/Lancer-vtt-NPC-import`, `scripts/pilot-reserves-patch.js`,
   `_refillResources`).
4. Доступ до хмари COMP/CON (з коду того ж модуля, `scripts/auth/cognito-auth.js`,
   `scripts/v3-api.js`):
   - вхід — AWS Cognito (SRP) з email і паролем COMP/CON; браузер може звертатися до Cognito
     напряму, проксі там лише запасний шлях;
   - після входу — токен входу (JWT, `Authorization`) і токен оновлення (REFRESH_TOKEN_AUTH);
   - список: `GET <v3ApiBase>/user?user_id=<sub>&scope=changed&since=0` із заголовками
     `x-api-key` і `Authorization`; записи мають `SortKey` (префікс типу), `uri`, `updated`,
     `deleted`; актуальний запис на `uri` — з найбільшим `updated`;
   - файл: `GET <v3Cdn>/<uri>`;
   - API неофіційний: адреси й ключ — з коду сайту COMP/CON; модуль виніс їх у
     налаштування на випадок зміни.
5. CORS-обмеження діє лише в браузері. Функції Supabase звертаються до API і CDN COMP/CON без
   проксі.
6. Апка вже вміє: розкласти мехів з файлу по слотах ангару (`slotImport.js`), оновити збірку
   меха й зберегти стан з апки (`mergeMechState`), зберегти файл на кожного меха
   (`pilot_compcon`), а модуль — створити з файлу актора.

7. **Share code перевірено** (17.10.2026, код тестового пілота користувача):
   - `GET https://api.compcon.app/v3/code?codes=["<код>"]&scope=items` із заголовком
     `x-api-key` (ключ із системи Lancer, `src/module/util/compcon.ts`) → `200`, масив
     `[{ code, uri, sortkey, name, author, version: 3, created, item_modified, updated, size }]`.
     Та сама відповідь — з адреси й ключа модуля Lancer Comp/Con Sync (`…execute-api…/prod/code`).
     Вхід не потрібен.
   - `GET https://ds69h3g1zxwgy.cloudfront.net/<uri>` → `200`, файл пілота **v3 без обгортки**
     (`itemType: "pilot"`, `id`, `level`, `callsign`, `name`, `mechs[]` з `frame`, `loadouts`, …).
   - Версія для порівняння — `updated` (мс) з відповіді `/code`; у файлі — `save.lastModified`
     (= `item_modified`).
   - Імпорт апки (`mapCompconPilot`) приймає лише експорт-обгортку
     `{ EXPORT_TYPE: "Save Pilot", data }`. Той самий файл, загорнутий так, імпортується без
     змін коду (перевірено: пілот, LL, мех, фрейм, ХП, 7 предметів).

## 1. Хто джерело правди

| Дані | Джерело | Куди йде |
|---|---|---|
| мана, PR, покращення, поліси, резерви апки | апка | → Foundry (показ) |
| ХП і стрес пілота, бонд (XP, галочки, мінорний ідеал, архетип, сили, burdens) | апка | ↔ Foundry для полів, що синхронізуються зараз; решта бонду — апка → Foundry (§5.1); з COMP/CON бонд не приймається |
| стан меха: ХП, структура, реактор, ремкомплекти, Overcharge, Core Power, заряди, знищене | апка | ↔ Foundry (бій), як зараз |
| білд: фрейм, лоадаут, таланти, скіли, ліцензії, корбонуси, мех-скіли | COMP/CON | → апка → Foundry |
| LL | апка | → Foundry, як зараз; LL з COMP/CON — лише для попередження (§3.3) |

## 2. Поняття

- **Акаунт COMP/CON** — підключається один раз на акаунт апки (Account manager).
- **Прив'язка пілота** — пілот апки ↔ пілот хмари COMP/CON (вибір зі списку акаунта).
- **Зв'язок слота** — слот ангару апки ↔ мех прив'язаного пілота COMP/CON. Пілот із двома
  профілями COMP/CON (різні таланти під різних мехів) — слоти з мехами двох пілотів COMP/CON.
- **Версія білду** — `updated` запису COMP/CON, з якого взято збірку меха.
- **Остання зміна** — коли апка останній раз підхопила зміни з COMP/CON (`ПРИЙНЯТИ`).

## 3. Сценарії гравця — дії й послідовність

### 3.1. Один раз: підключити COMP/CON (Account manager)

1. Меню → Account manager → блок `COMP/CON LINK`, під назвою — «Прив'яжіть свій акаунт з
   COMP/CON для синхронізації стану персонажів.»
2. Поля `EMAIL`, `ПАРОЛЬ`, кнопка `ПІДКЛЮЧИТИ`.
3. Вхід іде з браузера гравця напряму в COMP/CON (Cognito); пароль не передається апці й ніде
   не зберігається. Апці передається лише токен оновлення (§6).
4. Успіх → блок показує email акаунта COMP/CON і `ВІДКЛЮЧИТИ`.
   Помилка → рядок помилки з відповіді COMP/CON.

### 3.2. Один раз на пілота: прив'язати (профіль пілота)

1. Профіль пілота → блок `COMP/CON`. Два способи прив'язки, на пілота — один:
   - **з акаунта** (якщо `COMP/CON LINK` підключено): `ПІЛОТ COMP/CON` — список пілотів хмари
     гравця (позивний, ім'я, LL);
   - **за кодом** (акаунт не потрібен): поле `SHARE CODE` — код пілота з COMP/CON (12 символів
     для v3, 6 — для v2, як у системі Lancer).
2. Під кожним слотом ангару — `МЕХ COMP/CON`: мехи обраного пілота або `—` (слот не
   синхронізується). Типовий вибір — як у `defaultAssignment` (`ccId`, без нього — назва).
3. `ЗБЕРЕГТИ` → апка одразу забирає файл і показує зміни (§3.3, крок 4).

Слоти без зв'язку працюють, як зараз: ручне завантаження файлу.

**Де це в профілі** (макет — скриншоти справжньої апки з доданими елементами):
- рядок під панеллю «ПРОФІЛЬ ПІЛОТА», де зараз `ОНОВИТИ З COMP/CON JSON`: `SHARE CODE` (або
  `ПІЛОТ COMP/CON`, коли акаунт підключено), `СИНХРОНІЗУВАТИ З COMP/CON`, тег статусу COMP/CON,
  `РІВЕНЬ НЕ ЗБІГАЄТЬСЯ`; `ОНОВИТИ З COMP/CON JSON` лишається поруч;
- картка меха в «МЕХ АНГАР»: теги `COMP/CON · …` і `FOUNDRY · …` замість нинішніх
  `FOUNDRY · НЕ ЗВ'ЯЗАНО` / `ФАЙЛ ОНЛАЙН`; `МЕХ COMP/CON` (вибір) на місці кнопки
  `ОНОВИТИ З COMP/CON` слота — ручне завантаження файлу слота переходить у меню `⋯` меха;
- вікно змін — звичайне модальне вікно апки (`modal-box`).

На `/pilots` теги зведеного статусу — під рядком мехів у кожному рядку списку.
В Account manager (вікно «ДАНІ ВХОДУ») блок `COMP/CON LINK` — між DISCORD і НІКНЕЙМ.

### 3.3. Щоразу після зміни білду

1. **COMP/CON:** змінити білд.
2. **COMP/CON:** опублікувати зміни — без цього кроку апка їх не побачить (факти §0.1–0.2):
   - пілот прив'язаний з акаунта → синхронізація з хмарою в COMP/CON;
   - пілот прив'язаний за кодом → оновлення за share code в COMP/CON (перевірено користувачем:
     код показує лише опубліковану за ним версію).
3. **Апка:** профіль пілота → `СИНХРОНІЗУВАТИ З COMP/CON`.
4. **Апка:** є нова версія → вікно змін за групами `ФРЕЙМ`, `ЗБРОЯ`, `СИСТЕМИ`, `ТАЛАНТИ`
   (`+` додано, `−` прибрано), кнопки `ПРИЙНЯТИ` / `СКАСУВАТИ`. Порівняння по предметах —
   новий код: наявний `changesText` (`slotImport.js`) описує лише слоти.
   - LL у COMP/CON ≠ LL в апці → попередження над списком змін: «Рівень персонажу в файлі не
     відповідає рівню вашого персонажу.» Прийняти можна; LL не змінюється.
   - Бонд із файлу не приймається.
   - `ПРИЙНЯТИ` → збірка меха оновлюється через `mergeMechState` (стан з апки лишається),
     файл записується в `pilot_compcon` з новою версією; «остання зміна» — зараз. Статус
     FOUNDRY — «Зміна потребує підтвердження на Foundry».
5. **Foundry:** хаб → пілот → `СИНХРОНІЗУВАТИ ЗМІНИ З COMP/CON` (§4, §5).

### 3.4. Один раз: увійти в хаб Foundry

1. **Foundry:** панель акторів → кнопка хаба (§4). Без входу — поля `НІКНЕЙМ`, `ПАРОЛЬ` (як на
   сторінці входу апки) і кнопка входу.
2. Модуль входить в апку (Supabase Auth, той самий `nickToEmail`), зберігає сесію в
   **клієнтському** налаштуванні цього браузера; пароль не зберігається.
3. Гравець, який входить в апку лише через Discord, спершу задає пароль в Account manager
   (`ЗАДАТИ ПАРОЛЬ` — уже є).
4. Вихід — кнопка в хабі; сесію можна також завершити зміною пароля в апці.

### 3.5. Статуси (екран вибору пілотів, профіль, хаб)

**Статуси — на кожен мех (слот) окремо** (рішення користувача 17.10.2026): слоти можуть бути
прив'язані до різних пілотів COMP/CON і мати різних акторів. Пілот з одним мехом має одну пару
статусів, з двома — дві. Зведений статус пілота (картка на `/pilots`) — з усіх його мехів.

На мех (профіль — під слотом; хаб — рядок меха):

| Рядок | Статус | Коли |
|---|---|---|
| `COMP/CON` | «Код активний» // остання зміна (дата, час) | пілот прив'язаний, апка останній раз отримала файл без помилки |
| `COMP/CON` | «Код не активний» | не прив'язаний; код не знайдено; акаунт відключено / потрібен повторний вхід; пілота в хмарі немає; помилка COMP/CON |
| `FOUNDRY` | «Зміна потребує підтвердження на Foundry» | зв'язаний актор має старішу версію білду, ніж прийнята в апці |
| `FOUNDRY` | «Пілот готовий до завдання» | зв'язаний актор з актуальним білдом |
| `FOUNDRY` | «Синхронізація відсутня» | зв'язаного актора немає |

Зведений статус пілота (`/pilots`), зверху вниз:

| Рядок | Статус | Коли |
|---|---|---|
| `COMP/CON` | «Код активний» // найпізніша остання зміна | усі прив'язані мехи — «Код активний» |
| `COMP/CON` | «Код не активний» | хоч один прив'язаний мех — «Код не активний», або жодного не прив'язано |
| `FOUNDRY` | «Зміна потребує підтвердження на Foundry» | хоч один мех — так |
| `FOUNDRY` | «Пілот готовий до завдання» | усі мехи у слотах — так |
| `FOUNDRY` | «Частково готовий» | готові не всі мехи (наприклад, два мехи, актор лише в одного) |
| `FOUNDRY` | «Синхронізація відсутня» | жодного зв'язаного актора |
 Апка знає про акторів із `foundry_mech_links`
(звіт модуля, уже є) і версію білду актора — з того ж звіту (§7.2).
Якщо LL у файлі ≠ LL в апці, у профілі й хабі ще `РІВЕНЬ НЕ ЗБІГАЄТЬСЯ`.

### 3.6. Проблеми

| Що | Що бачить гравець | Що робити |
|---|---|---|
| токен COMP/CON більше не діє | «Код не активний»; у `COMP/CON LINK` — `ПОТРІБЕН ПОВТОРНИЙ ВХІД` | §3.1 ще раз |
| COMP/CON недоступний або змінив API | «Код не активний», текст помилки в профілі | білд лишається останнім прийнятим |
| пілота або меха немає в хмарі | «Код не активний» | обрати іншого (§3.2) |
| сесія хабу завершилась | хаб показує вхід | §3.4 ще раз |

## 4. Хаб у Foundry (замість вікна «Зв'язки з апкою»)

Зразок — вікно Lancer Comp/Con Sync (скриншот користувача 17.10.2026).

- **Вхід** — §3.4. Кнопка хаба — у панелі акторів (для всіх) і в налаштуваннях модуля.
- **Ліворуч** — список: **рядок на кожен мех** (пара «пілот + мех» = окремий актор; пілот з
  двома мехами — два рядки), гравцю — свої, ГМу — усі. Рядок: портрет, ім'я пілота, мех і фрейм,
  LL, крапка статусу `FOUNDRY` цього меха (§3.5). Пошук за іменем, позивним, фреймом; фільтри
  за статусами `FOUNDRY` з кількістю.
- **Праворуч** — обраний рядок (пілот + мех):
  - шапка: портрет, ім'я, позивний, LL, рядки `COMP/CON` і `FOUNDRY` цього меха (§3.5);
  - мана, PR / кап (з апки, спільні для пілота);
  - мех (з апки): слот, назва, фрейм, зв'язаний актор;
  - з файлу COMP/CON: HULL / AGI / SYS / ENG, таланти, ліцензії, скіли, корбонуси;
  - бонд — з апки (§0.1.5);
  - дії: `СТВОРИТИ АКТОРА` (мех без актора, є файл) і `СИНХРОНІЗУВАТИ ЗМІНИ З COMP/CON`
    (є новіша прийнята версія).
- **Тільки ГМ** — ручне зв'язування з наявним актором і `Синхронізувати зараз` (як у
  нинішньому вікні зв'язків), налаштування модуля.
- Нинішнє обмеження «Створювати акторів можуть лише ГМи» (`createFromApp`) знімається — §4.2.

### 4.1. Одна кнопка на пілота і перевірка при відкритті (рішення користувача 17.10.2026)

Зразок — Lancer Comp/Con Sync: гравець натискає одну кнопку, хаб сам перевіряє стан при кожному
відкритті.

- **Перевірка при відкритті хабу** (і при виборі пілота): модуль шукає у світі зв'язаних акторів
  (прапорці `pilotId` / `mechId`) і їхню версію білду. Актора видалили → статус `FOUNDRY` одразу
  змінюється («Частково готовий» / «Синхронізація відсутня»), а модуль звітує новий список
  зв'язків в апку (дія `links`, як зараз — тепер і з браузера гравця, §7.3).
- **Одна головна кнопка рядка (меха)** — за станом:
  - актора немає → `СТВОРИТИ АКТОРА`;
  - актор є, прийнята в апці версія новіша → `СИНХРОНІЗУВАТИ ЗМІНИ З COMP/CON`;
  - усе готово → кнопки немає, статус «Пілот готовий до завдання».

### 4.2. Власник актора — гравець

Актор, створений для пілота, одразу належить гравцю цього пілота (рівень `OWNER`), без ручної
видачі прав ГМом.

- **Хто з користувачів Foundry — гравець пілота.** Під час входу в хаб (§3.4) модуль записує на
  користувача Foundry прапорець `flags.silent-stars-sync.appUserId` (акаунт апки). Пілот апки
  має `user_id` власника → користувач Foundry з тим самим `appUserId`.
- **Створює гравець сам.** Foundry робить власником того, хто створив актора (не-ГМа). Але
  створювати акторів гравцям дозволяє лише налаштування світу «Створювати нових акторів»
  (Налаштування → Права користувачів, роль Гравець) — його вмикає ГМ один раз. Вимкнено →
  кнопка гравця неактивна з написом `ПОТРІБЕН ДОЗВІЛ ГМА НА СТВОРЕННЯ АКТОРІВ`.
- **Створює ГМ** (за гравця): модуль ставить `ownership` пілота й меха = `OWNER` для
  користувача Foundry з відповідним `appUserId`. Гравець ще не входив у хаб → власника немає,
  ГМ видає права вручну (як зараз).
- Для вже створених зв'язаних акторів — те саме при наступному відкритті хабу ГМом, якщо
  власник не заданий.
- Меха, якого створює імпорт системи в браузері гравця, власником одразу стає гравець
  (перевірено користувачем).
- Арти в Data гравець може класти з дозволом «Завантажувати нові файли» (права користувачів,
  ГМ вмикає) — перевірено користувачем. Без дозволу арт кладе браузер ГМа, як зараз.

## 5. Синхронізація змін з COMP/CON у Foundry

Хто запускає: `СИНХРОНІЗУВАТИ ЗМІНИ З COMP/CON` у хабі — гравець або ГМ. **ГМ у грі не
потрібен**: присутність ГМа потрібна лише для пасивної синхронізації стану з апкою.

- Гравець оновлює актора у своєму браузері. Foundry дає йому змінювати лише акторів, власником
  яких він є (пілот і мех — права видає ГМ), тож чужих персонажів він не зачепить.
- Файл гравець отримує своєю сесією апки (§3.4, §7.3) — лише файли своїх пілотів.
- ГМ — те саме для будь-якого зв'язаного актора.

Кроки:

1. Позначка `creating` (як при створенні), щоб цикл синхронізації ГМа, якщо він іде, не чіпав
   актора й меха.
2. Знімок стану актора й меха **до** імпорту: ХП і стрес пілота, ХП, структура, реактор,
   ремкомплекти, Overcharge, Core Power меха, заряди й «знищено» предметів (за назвою), LL.
3. Імпорт файлу системою Lancer у **той самий** актор-пілот (`_onPilotJsonParsed`, як у
   `createFromApp`).
4. Повернути знімок поверх наповнення імпортом (факт §0.3): у предметів, які лишились (та сама
   назва), — їхні заряди, «знищено» і прапорець `base`; нові предмети — як з імпорту.
5. Записати `flags.silent-stars-sync.build = <версія>`, зняти `creating`.

Стан бою не скидається: значення в акторі ті самі, що до імпорту, а наступний цикл ГМа зводить
їх з апкою за звичайними правилами. Нові макс. значення з нового лоадауту — Foundry → апка,
як зараз.

### 5.1. Бонд з апки (рішення користувача 17.10.2026)

Архетип (бонд), сили й burdens актора-пілота йдуть з апки → Foundry, як і решта бонду. Зараз
модуль їх не синхронізує (`docs/foundry-sync.md`), і вони приходять з файлу COMP/CON при
створенні актора.

До коду — дослідити, як система Lancer зберігає їх в акторі (предмет типу `bond`, сили бонду,
`system.bond_state.burdens` / `clocks`), і зіставити з `state.bond` апки. Напрямок — лише
апка → Foundry; зміни в акторі перезаписуються наступним циклом. Після повторного імпорту
білду (§5) вони так само беруться з апки, а не з файлу.

## 6. Дані

### 6.1. `public.compcon_accounts`

| Колонка | Тип | |
|---|---|---|
| `user_id` | uuid pk → auth.users | |
| `cc_sub`, `cc_email` | text | користувач COMP/CON |
| `token_secret` | uuid | id секрету у `vault.secrets` (токен оновлення) |
| `connected_at`, `checked_at` | timestamptz | |
| `error` | text | остання помилка або `''` |

RLS: власник читає свій рядок **без** `token_secret`; писати — лише функція `compcon-link`
(service_role). Токен оновлення не повертається клієнту ніколи.

### 6.2. Прив'язка пілота й слотів

- `pilots` — у `state` або окремою таблицею (вирішити в коді): `cc_pilot_id`, `cc_uri` (з
  акаунта) або `cc_code` (share code).
- `pilot_compcon` — нові колонки `cc_mech_id text`, `cc_updated bigint` (версія),
  `accepted_at timestamptz` (остання зміна), `checked_at timestamptz`, `error text`.
  `cc_mech_id is null` — слот без зв'язку (ручний файл, як зараз).

### 6.3. `public.foundry_mech_links` — нова колонка

`build bigint` — версія білду актора (з `flags.silent-stars-sync.build`), для статусу §3.5.

## 7. Функції

### 7.1. `compcon-link` (verify_jwt = true, гравець)

- `connect { refreshToken, sub, email }` → перевіряє токен оновленням у Cognito, кладе у vault,
  створює / оновлює `compcon_accounts`.
- `disconnect` → видаляє секрет і рядок.
- `list` → пілоти хмари гравця: `{ id, uri, updated, callsign, name, level, mechs: [{ id, name, frame }] }`.
- `fetch { pilotId }` → свіжий файл прив'язаного пілота (з акаунта — токеном гравця; за кодом —
  `GET <v3ApiBase>/code?scope=item&codes=["<код>"]` із загальним `x-api-key`, далі файл з CDN за
  `uri`, як `share-code-test.js` модуля Lancer Comp/Con Sync; вхід не потрібен), `updated`,
  `level`; пише `checked_at`,
  `error`. Прийняття — у клієнті через наявний імпорт (`compconFile.js`).

Адреси й ключ API COMP/CON — секрети функції (`CC_API_BASE`, `CC_API_KEY`, `CC_CDN`,
`CC_COGNITO_CLIENT_ID`).

### 7.2. `foundry-sync` — доповнення

- `pull`: у меха — `build` (`cc_updated`).
- `links`: модуль звітує й версію білду актора (`build`).

### 7.3. `foundry-hub` (verify_jwt = true — сесія апки з хабу)

RLS як в апці: гравець — свої пілоти, ГМ — усі.
- `list` → пілоти з даними правої панелі (§4) і статусами (§3.5).
- `profile { pilotId, mechId }` → файл COMP/CON меха (§5).
- `links { world, links }` → звіт зв'язків з браузера гравця — лише для його пілотів (§4.1).
- (за бажанням) дії магазину від імені гравця.

## 9. Відкриті питання

Раніше затверджені написи (`EMAIL`, `ПАРОЛЬ`, `ПІДКЛЮЧИТИ`, `ВІДКЛЮЧИТИ`,
`ПОТРІБЕН ПОВТОРНИЙ ВХІД`, `МЕХ COMP/CON`, `ЗБЕРЕГТИ`, `ПРИЙНЯТИ`, `СКАСУВАТИ`,
`РІВЕНЬ НЕ ЗБІГАЄТЬСЯ`) лишаються. Затвердити нові:

1. `ПІЛОТ COMP/CON` і `SHARE CODE` (профіль, §3.2).
   До коду перевірити на справжньому коді, що відповідає `/code` (поле `uri`, версія `updated`),
   — у цій сесії це не перевірено.
2. Групи змін `ФРЕЙМ` / `ЗБРОЯ` / `СИСТЕМИ` / `ТАЛАНТИ` (§3.3).
3. Хаб: назва вікна й кнопки, кнопка входу, кнопка виходу (§3.4, §4). `НІКНЕЙМ` і `ПАРОЛЬ` —
   як на сторінці входу апки.
