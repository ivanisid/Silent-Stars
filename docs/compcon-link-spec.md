# Зв'язок апки з акаунтом COMP/CON і вхід гравця в модуль Foundry

Перед початком: прочитати `CLAUDE.md`, `docs/overview.md`, `docs/foundry-sync.md`. Зразки:
імпорт файлу COMP/CON у слоти ангару (`client/src/pilot/compconFile.js`, `slotImport.js`,
`mechMerge.js`), синхронізація з Foundry (`supabase/functions/foundry-sync`,
`foundry-module/silent-stars-sync`).

Статус: **погоджено 17.10.2026** (рішення — §0.1). Написи §3–4 затверджено; нові написи, яких
там немає, затверджує користувач до коду (CLAUDE.md: лише продуктові тексти, без пояснювальних
підписів).

Завдання (від користувача):
1. Гравець змінює білд у COMP/CON і не завантажує файл в апку щоразу вручну.
2. Три джерела правди: апка — мана, PR і стан пілота й меха; COMP/CON — білд; Foundry — бій.
3. Гравець підключає свій акаунт COMP/CON в апці; апка й гравець бачать, що синхронізується,
   а що ні. Ці дані використовує й модуль Foundry.
4. Гравець входить у модуль Foundry через акаунт апки (не через COMP/CON) і сам бачить стан
   синхронізації.
5. Дії гравця мають бути зрозумілими — їхня послідовність прописана в §3.

## 0.1. Рішення користувача (17.10.2026)

1. **LL** — джерело правди апка. Рівень з COMP/CON не приймається; якщо він відрізняється від LL
   в апці (гравець міг змінити його в COMP/CON ненавмисно), апка показує попередження.
2. **Нова версія** — лише кнопкою апки `СИНХРОНІЗУВАТИ З COMP/CON`; автоматичної перевірки за розкладом немає.
   Прийняття — вручну.
3. **Ручне завантаження JSON** лишається запасним шляхом.
4. **Оновлення актора у Foundry** — гравець сам у вікні модуля; ГМ теж може.
5. **Бонд** — лише в апці; з COMP/CON не приймається. Архетип, сили й burdens бонду в
   акторі Foundry теж ідуть з апки (§5.1).
6. Написи §3–4 — затверджено.
7. Неофіційний API COMP/CON — на ризик проєкту, погоджено.

## 0. Встановлені факти (17.10.2026)

1. Файл у хмарі COMP/CON оновлюється **лише вручну** — спеціальною кнопкою синхронізації в
   COMP/CON (перевірено користувачем). Автозбереження в хмару немає.
2. Share code показує версію, яку гравець опублікував за кодом; модуль Lancer Comp/Con Sync
   бачить її лише після цього (перевірено користувачем).
3. Повторний імпорт актора в Foundry (і системний, і через Lancer Comp/Con Sync) наповнює ХП,
   структуру, стрес і ремкомплекти до максимуму, обнуляє heat, burn, overshield і створює
   предмети наново (код `Agraael/Lancer-vtt-NPC-import`, `scripts/pilot-reserves-patch.js`,
   `_refillResources`).
4. Доступ до хмари COMP/CON (з коду того ж модуля, `scripts/auth/cognito-auth.js`,
   `scripts/v3-api.js`):
   - вхід — AWS Cognito (SRP) з email і паролем COMP/CON; браузер може звертатися до Cognito
     напряму, проксі там лише запасний шлях;
   - після входу — токен входу (JWT, `Authorization`) і токен оновлення (REFRESH_TOKEN_AUTH);
   - список: `GET <v3ApiBase>/user?user_id=<sub>&scope=changed&since=0` із заголовками
     `x-api-key` і `Authorization`; записи мають `SortKey` (префікс типу), `uri`, `updated`,
     `deleted`; актуальний запис на `uri` — з найбільшим `updated`;
   - файл: `GET <v3Cdn>/<uri>`;
   - API неофіційний: адреси й ключ — з коду сайту COMP/CON; модуль виніс їх у
     налаштування на випадок зміни.
5. CORS-обмеження діє лише в браузері. Функції Supabase звертаються до API і CDN COMP/CON без
   проксі.
6. Апка вже вміє: розкласти мехів з файлу по слотах ангару (`slotImport.js`), оновити збірку
   меха й зберегти стан з апки (`mergeMechState`), зберегти файл на кожного меха
   (`pilot_compcon`), а модуль — створити з файлу актора.

## 1. Хто джерело правди

| Дані | Джерело | Куди йде |
|---|---|---|
| мана, PR, покращення, поліси, резерви апки | апка | → Foundry (показ) |
| ХП і стрес пілота, бонд (XP, галочки, мінорний ідеал, архетип, сили) | апка | ↔ Foundry для полів, що синхронізуються зараз; з COMP/CON бонд не приймається |
| стан меха: ХП, структура, реактор, ремкомплекти, Overcharge, Core Power, заряди, знищене | апка | ↔ Foundry (бій), як зараз |
| білд: фрейм, лоадаут, таланти, скіли, ліцензії, корбонуси, мех-скіли | COMP/CON | → апка → Foundry |
| LL | апка | → Foundry, як зараз; LL з COMP/CON — лише для попередження (§3.3) |

Правило для білду: COMP/CON → апка — лише коли гравець **прийняв** нову версію (§3.3).
Апка → Foundry — нова версія збірки меха, далі §5.

## 2. Нові поняття для гравця

- **Акаунт COMP/CON** — підключається один раз на акаунт апки.
- **Зв'язок слота** — слот ангару апки ↔ мех конкретного пілота COMP/CON. Один слот — один мех.
  Пілот із двома профілями COMP/CON (різні таланти під різних мехів) — два слоти з мехами
  двох різних пілотів COMP/CON; так само, як зараз з двома файлами.
- **Версія білду** — `updated` запису COMP/CON, з якого взято збірку меха.
- **Foundry підключено** — Foundry гравця має власний доступ до апки (§4).

## 3. Сценарії гравця — дії й послідовність

### 3.1. Один раз: підключити COMP/CON

1. Профіль пілота → меню `⋯` → `COMP/CON`.
2. Вікно `ПІДКЛЮЧИТИ COMP/CON`: поля `EMAIL`, `ПАРОЛЬ`, кнопка `ПІДКЛЮЧИТИ`.
3. Вхід іде з браузера гравця напряму в Cognito; пароль не передається апці й ніде не
   зберігається. Апці передається лише токен оновлення (§6).
4. Успіх → вікно переходить у §3.2.
   Помилка → рядок помилки з відповіді Cognito (невірний пароль, акаунт не знайдено тощо).

### 3.2. Один раз на пілота: зв'язати мехів зі слотами

1. Вікно `COMP/CON` показує пілотів хмари COMP/CON гравця: позивний, ім'я, LL, мехи.
2. Під кожним слотом ангару апки — вибір `МЕХ COMP/CON`: список «пілот · мех» або `—`
   (слот не синхронізується).
3. Типовий вибір — як у `defaultAssignment`: мех із тим самим ідентифікатором COMP/CON
   (`ccId`), без нього — з тією ж назвою.
4. `ЗБЕРЕГТИ` → апка одразу завантажує обрані файли і показує зміни (§3.3, крок 4).

Слоти без зв'язку працюють, як зараз: ручне завантаження файлу (§9.3).

### 3.3. Щоразу після зміни білду

1. **COMP/CON:** змінити білд.
2. **COMP/CON:** натиснути кнопку синхронізації з хмарою. Без цього кроку апка змін не побачить
   (факт §0.1).
3. **Апка:** профіль пілота → `COMP/CON` → `СИНХРОНІЗУВАТИ З COMP/CON`. Автоматичної перевірки
   немає.
   - Версія та сама → статус `АКТУАЛЬНО`.
   - Версія новіша → статус `Є НОВА ВЕРСІЯ`.
4. **Апка:** `ПЕРЕГЛЯНУТИ` → список змін (`changesText` з `slotImport.js`: фрейм, зброя,
   системи, таланти…), кнопки `ПРИЙНЯТИ` / `СКАСУВАТИ`.
   - LL у COMP/CON ≠ LL в апці → попередження над списком змін:
     `Рівень персонажу в файлі не відповідає рівню вашого персонажу.` Прийняти можна; LL не змінюється.
   - Бонд із файлу не приймається (`mapCompconBond` при прийнятті не викликається).
   - `ПРИЙНЯТИ` → збірка меха оновлюється через `mergeMechState` (стан з апки лишається),
     файл записується в `pilot_compcon` з новою версією. Статус слота — `ПРИЙНЯТО`, у
     Foundry — `ЧЕКАЄ FOUNDRY`.
5. **Foundry (гравець):** вікно `SILENT STARS` → у слоті `ЧЕКАЄ FOUNDRY` → `ОНОВИТИ БІЛД`.
   Те саме може зробити ГМ у вікні зв'язків (§4). Після оновлення статус — `У FOUNDRY`.

### 3.4. Один раз: підключити Foundry

1. **Foundry (гравець):** налаштування модуля → `ПІДКЛЮЧИТИ SILENT STARS`. Модуль показує
   код з 8 символів і кнопку `ВІДКРИТИ АПКУ`.
2. **Апка:** сторінка `/link?code=…` (відкривається кнопкою) → `ПІДКЛЮЧИТИ FOUNDRY` — вхід в
   апку, якщо потрібно, і підтвердження.
3. **Foundry:** модуль сам дізнається, що код підтверджено (опитування раз на 3 с, код
   живе 10 хв), і зберігає свій токен у **клієнтському** налаштуванні цього браузера.
4. **Апка:** профіль акаунта → список підключених Foundry (світ, дата, `ВІДКЛЮЧИТИ`).

### 3.5. Будь-коли: перевірити стан синхронізації

Однакова таблиця статусів в апці (`COMP/CON` у профілі пілота) і в модулі (вікно
`SILENT STARS` гравця). На кожен слот:

| Колонка | Значення |
|---|---|
| `СЛОТ` | номер і назва меха |
| `COMP/CON` | `АКТУАЛЬНО` / `Є НОВА ВЕРСІЯ` / `НЕ ЗВ'ЯЗАНО` / `ПОМИЛКА` + дата версії; якщо LL у COMP/CON ≠ LL в апці — ще `РІВЕНЬ НЕ ЗБІГАЄТЬСЯ` |
| `FOUNDRY` | `У FOUNDRY` / `ЧЕКАЄ FOUNDRY` / `НЕМАЄ АКТОРА` + час останньої синхронізації; у модулі біля `ЧЕКАЄ FOUNDRY` — `ОНОВИТИ БІЛД` |

Модуль показує лише пілотів власника токена. ГМ у вікні зв'язків бачить статус `FOUNDRY` усіх.

### 3.6. Проблеми

| Що | Що бачить гравець | Що робити |
|---|---|---|
| токен COMP/CON більше не діє | `COMP/CON` → `ПОТРІБЕН ПОВТОРНИЙ ВХІД` | §3.1 ще раз |
| COMP/CON недоступний або змінив API | `ПОМИЛКА` з текстом відповіді | нічого не ламається: білд лишається останнім прийнятим |
| мех зник із хмари COMP/CON (видалено) | `ПОМИЛКА` у слоті | зв'язати слот з іншим мехом або `—` |
| Foundry відключено в апці | модуль: `НЕ ПІДКЛЮЧЕНО` | §3.4 ще раз |

Відключити COMP/CON: вікно `COMP/CON` → `ВІДКЛЮЧИТИ` — токен видаляється з vault, зв'язки
слотів лишаються, але не перевіряються.

## 4. Сценарії ГМа

1. Створення актора — як зараз (`Створити актора` у вікні зв'язків), з файлу `pilot_compcon`.
2. У вікні зв'язків біля меха — статус `FOUNDRY` і кнопка `ОНОВИТИ БІЛД` для слотів
   `ЧЕКАЄ FOUNDRY`; у шапці — `ОНОВИТИ ВСІ (N)`. Ті самі слоти гравець оновлює сам (§3.3, крок 5).
3. Повторний імпорт через Lancer Comp/Con Sync або системну кнопку на зв'язаних акторах не
   потрібен; модуль його не блокує, але після нього стан перезапишеться з апки (§5, крок 3).

## 5. Оновлення білду у Foundry

Хто запускає: кнопка `ОНОВИТИ БІЛД` гравця (вікно `SILENT STARS`) або ГМа (вікно зв'язків).
**ГМ у грі не потрібен** (рішення користувача 17.10.2026): присутність ГМа потрібна лише для
пасивної синхронізації стану з апкою.

- Гравець оновлює актора у своєму браузері. Foundry дає йому змінювати лише акторів, власником
  яких він є (пілот і мех — права видає ГМ), тож чужих персонажів він не зачепить.
- Файл білду гравець отримує своїм токеном (§3.4, §7.3 `profile`) — лише файли своїх пілотів.
  Ключ синхронізації ГМа гравцю не потрібен.
- ГМ робить те саме у своєму браузері для будь-якого зв'язаного актора; файл — через
  `foundry-sync` (`profile`, як зараз).

Для зв'язаного актора, у якого версія білду в апці новіша за прапорець
`flags.silent-stars-sync.build` актора-пілота:

1. Позначка `creating` (як при створенні), щоб цикл синхронізації ГМа, якщо він іде, не чіпав
   актора й меха.
2. Знімок стану актора й меха **до** імпорту: ХП і стрес пілота, ХП, структура, реактор,
   ремкомплекти, Overcharge, Core Power меха, заряди й «знищено» предметів (за назвою), LL.
3. Імпорт файлу системою Lancer у **той самий** актор-пілот (`_onPilotJsonParsed`, як у
   `createFromApp`).
4. Повернути знімок (крок 2) поверх наповнення імпортом (факт §0.3): у предметів, які лишились
   (та сама назва), — їхні заряди й «знищено» та прапорець `base`; нові предмети — як з імпорту.
   Прапорці `base` актора й меха не змінюються.
5. Записати `flags.silent-stars-sync.build = <версія>`, зняти `creating`.

Так стан бою не скидається і не залежить від того, чи був ГМ: значення в акторі лишаються ті
самі, що були до імпорту, а наступний цикл ГМа зводить їх з апкою за звичайними правилами
(§«Конфлікти» у `docs/foundry-sync.md`). Нові макс. значення з нового лоадауту (ХП, заряди)
Foundry → апка, як зараз.

Поля бонду — §5.1.

### 5.1. Бонд з апки (рішення користувача 17.10.2026)

Архетип (бонд), сили й burdens актора-пілота йдуть з апки → Foundry, як і решта бонду. Зараз
модуль їх не синхронізує (`docs/foundry-sync.md`), і вони приходять з файлу COMP/CON при
створенні актора.

До коду — дослідити, як система Lancer зберігає їх в акторі (предмет типу `bond`, сили бонду,
`system.bond_state.burdens` / `clocks`), і зіставити з `state.bond` апки. Напрямок — лише
апка → Foundry; зміни в акторі перезаписуються наступним циклом. Після повторного імпорту
білду (§5) вони так само беруться з апки, а не з файлу.

Те саме правило (крок 3) застосовується, коли модуль бачить, що предмети меха створено
наново без його участі (повторний імпорт сторонніми засобами).

## 6. Дані

### 6.1. `public.compcon_accounts`

| Колонка | Тип | |
|---|---|---|
| `user_id` | uuid pk → auth.users | |
| `cc_sub` | text | `sub` користувача COMP/CON |
| `token_secret` | uuid | id секрету у `vault.secrets` (токен оновлення) |
| `connected_at`, `checked_at` | timestamptz | |
| `error` | text | остання помилка або `''` |

RLS: власник читає свій рядок **без** `token_secret`; писати — лише функція `compcon-link`
(service_role). Токен оновлення не повертається клієнту ніколи.

### 6.2. `public.pilot_compcon` — нові колонки

`cc_pilot_id text`, `cc_uri text`, `cc_updated bigint` (версія), `remote_updated bigint`
(остання побачена версія в хмарі), `checked_at timestamptz`, `error text`.
`cc_uri is null` — слот без зв'язку (ручний файл, як зараз).

### 6.3. `public.foundry_player_tokens`

`id uuid pk`, `user_id uuid`, `world text`, `token_hash text` (sha-256, сам токен у базі не
лежить), `created_at`, `last_used_at`, `revoked_at`.
Коди підключення — `public.foundry_link_codes (code text pk, token_hash text, user_id uuid
null, world text, expires_at)`.

## 7. Функції

### 7.1. `compcon-link` (verify_jwt = true, гравець)

- `connect { refreshToken, sub }` → перевіряє токен оновленням у Cognito, кладе у vault,
  створює / оновлює `compcon_accounts`.
- `disconnect` → видаляє секрет і рядок.
- `list` → пілоти хмари гравця: `{ id, uri, updated, callsign, name, level, mechs: [{ id, name, frame }] }`.
- `check { pilotId }` → для зв'язаних слотів пілота: свіжий `updated` і `level` пілота COMP/CON
  (для попередження про LL); пише `remote_updated`, `checked_at`, `error`.
- `fetch { pilotId, slot }` → файл COMP/CON для слота (як файл з диска) — далі прийняття
  в клієнті через наявний імпорт (`compconFile.js`), запис у `pilot_compcon` з `cc_updated`.

Адреси й ключ API COMP/CON — секрети функції (`CC_API_BASE`, `CC_API_KEY`, `CC_CDN`,
`CC_COGNITO_CLIENT_ID`), щоб змінити їх без розгортання коду.

### 7.2. `foundry-sync` — доповнення

- `pull`: у меха — `build` (`cc_updated` або `updated_at` файлу) і `buildPending`.
- `link-start { world }` → `{ code }`; `link-poll { code }` → `{ token }` після підтвердження.

### 7.3. `foundry-player` (verify_jwt = false, заголовок `x-player-token`)
